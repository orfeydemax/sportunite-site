# GitHub Repo Scout (Разведчик репозиториев)

Этот автономный навык предназначен для поиска, анализа и интеграции сторонних GitHub-репозиториев в архитектуру текущего проекта.

## ⚠️ Критическое правило: Обязательное подтверждение

**Никогда** не скачивайте и не модифицируйте файлы текущего проекта для интеграции нового репозитория без **явного разрешения пользователя**.

Рабочий процесс всегда должен выглядеть так:
1. Поиск и анализ.
2. Отчет пользователю с выбором лучшего кандидата и запросом на интеграцию (используйте инструмент `notify_user` с `BlockedOnUser=true`).
3. Ожидание ответа пользователя ("Да" или "Нет").
4. Только после "Да" — клонирование и интеграция.

---

## Рабочий процесс (Workflow)

При активации этого навыка строго следуйте этим 4 этапам:

### Этап 1: Анализ контекста (Preparation)
Прежде чем искать на GitHub, вы должны четко понимать, что ищете.
1. Проанализируйте `task.md`, `walkthrough.md` или `implementation_plan.md` текущего проекта, чтобы понять архитектуру и пайплайн.
2. Определите, какой именно функциональности не хватает или какую часть логики хочет улучшить пользователь.
3. Сформулируйте поисковые запросы для GitHub на основе нужного стека технологий (например, Python, FFmpeg, Playwright) и задачи (например, "TikTok uploader", "AI shorts generator", "video transcription").

### Этап 2: Поиск и отбор (Scouting)
1. Используйте доступные вам инструменты (например, `search_web` или браузер, также можно использовать MCP-инструменты GitHub `mcp_github-mcp-server_search_repositories`, если они доступны) для поиска репозиториев на GitHub по сформулированным запросам. Удобный путь: `https://github.com/search?q={query}&type=repositories`.
2. Найдите 3-5 репозиториев-кандидатов.
3. Внимательно проанализируйте каждый кандидат:
   - Прочтите их `README.md` (через скачивание или `read_url_content`).
   - Оцените актуальность (дата последнего коммита).
   - Оцените популярность (звезды/форки).
   - Проанализируйте зависимости (какие библиотеки нужны, нет ли конфликтов с текущим проектом).
   - Оцените сложность внедрения в текущий пайплайн.
4. Выберите **ОДИН лучший репозиторий**, который наиболее гладко впишется в текущую логику проекта пользователя.

### Этап 3: Запрос разрешения (The Checkpoint)
Сформируйте подробный отчет для пользователя и **обязательно остановитесь**, ожидая его ответа.

Используйте инструмент `notify_user` (с параметром `BlockedOnUser: true`).

**Формат отчета для пользователя (придерживайтесь этого шаблона в сообщении):**
```markdown
Я проанализировал GitHub и выбрал лучшие решения для внедрения в наш проект.

**🏆 Победитель: [Название репозитория](URL)**
- **Почему он лучший:** Краткое обоснование (совпадение по стеку, понятная архитектура, нужные функции).
- **Что он делает:** Суть репозитория в 1-2 предложениях.
- **Как это впишется в наш пайплайн:** Точечное описание, какие файлы/модули нашего проекта будут затронуты.

**Другие рассмотренные варианты (почему отклонены):**
- [Название 2](URL): причина отклонения (например, устарел или слишком монолитный).
- [Название 3](URL): причина отклонения.

❓ **Интегрируем репозиторий [Название победителя] в наш проект? (Да / Нет)**
```

### Этап 4: Интеграция (Integration - ТОЛЬКО после согласия)
Если пользователь отвечает "Да":
1. Клонируйте репозиторий в директорию `external_repos/` (или другую подходящую директорию проекта). Рекомендуется использовать: `git clone <URL> external_repos/<имя_папки>`.
2. Изучите структуру скачанного репозитория (найдите ключевые скрипты/модули).
3. Составьте план интеграции (`implementation_plan.md`), в котором опишите, как именно код из нового репозитория будет подключен к существующим скриптам проекта.
4. Реализуйте план, модифицируя целевые файлы проекта.
5. Обновите зависимости (допишите нужные пакеты в `requirements.txt` или `.env`).
6. После завершения интеграции проверьте работоспособность кода и создайте/обновите `walkthrough.md` с описанием того, как новая интеграция работает.

Если пользователь отвечает "Нет":
1. Спросите, какие у него есть другие пожелания к репозиторию или завершите задачу.
